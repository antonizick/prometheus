# 2026-09-11 — Phase 3 built

Fifth session of the day, after Phases 0-2. This is the "highest value"
phase per docs/04: Claude Code narrates itself, through `bin/prometheus-claude`
wired into `~/.claude/settings.json`'s `Stop` and `Notification` hooks.

## Task 3.1 came first, for real

Before writing any handler code, the actual hook payload schema was verified
two independent ways rather than assumed or taken from a first LLM-guessed
answer (asked via the `claude-code-guide` agent, per docs/09's instruction):

1. A throwaway probe hook (`experiments/hook-schema-probe.sh`, since deleted)
   was registered for both events and fired for real via `claude -p ...
   --model haiku` subprocesses. Captured a genuine `Stop` payload —
   `experiments/hook-payloads-raw.jsonl`.
2. `strings` against the installed `claude` binary itself
   (`~/.local/share/mise/installs/claude/2.1.268/claude` — a bun-compiled
   executable that still carries its bundled JS as readable UTF-8, including
   its own zod-style schema definitions) turned up the real `Notification`
   schema and the real `hooks` registration schema in `settings.json`,
   verbatim.

Full writeup: `experiments/hook-schema-findings.md`. Headline finding: the
guide agent's cold-guess answer was roughly half right, half invented — it
fabricated a `notification_data: {tool_name, tool_input}` structure that
doesn't exist (the real field is a flat `message` string plus a
`notification_type` enum tag) and a `tool_calls` array on `Stop` that isn't
there either, but it did correctly guess `last_assistant_message` and the
`"async": true` hook field. This is exactly the failure mode task 3.1 exists
to catch, and it would have shipped silently if the first answer had been
trusted.

A pty-driven attempt to force a real interactive permission prompt (to
capture `Notification` live, the same way `Stop` was captured) was correctly
blocked by this machine's own auto-mode classifier as a permission-prompt
bypass pattern. Abandoned in favor of the binary-schema method, which turned
out more informative anyway (it's ground truth for the *whole* schema, not
just whatever one test run happens to trigger).

## Two real bugs caught in testing, before anything spoke live

Both found by testing against mocked `say()`/`summarize()` first, and against
the real phrase bank / `/proc` second, before ever letting the real daemon
speak (Nick was warned before that final step, per
[[prometheus-audible-test-warning]]):

1. **A `Log.emit(event, ...)` naming collision.** Several call sites did
   `LOG.warn("some.event", "...", event=some_value)` — but `event` is
   `Log.emit`'s own positional parameter (the log line's own event name), so
   the kwarg collided with it and raised `TypeError` **inside the crash
   handler itself**, which meant the process exited non-zero instead of the
   guaranteed 0. Exactly the kind of bug the "must never block or slow a
   Claude turn" contract cannot tolerate, and it would only ever have shown
   up on the empty-message or notification paths, both easy to miss without
   the direct-invocation testing done here. Fixed by renaming the field to
   `bank_event` / `hook_event` at each call site.
2. **The path-stripping regex left `src` dangling.** Copied the leading
   pattern from `prometheus-llm`'s `post_filter` (`(?:[~.]?/[\w.\-]+){1,}`),
   which requires a leading `/` and so only matches from the first slash
   onward — fine there, because that regex is a backstop over text an LLM
   already rewrote in prose. Here it's the *only* sanitizer on the
   short-circuit path, and "src/auth/middleware.ts" has no leading slash, so
   the old pattern stripped "/auth/middleware.ts" and left a bare "src"
   sitting in the spoken sentence. Fixed by dropping the leading-slash
   requirement (`[~\w.\-]*/[\w.\-]+(?:/[\w.\-]+)*`) so it matches from the
   first path-looking segment regardless of whether it starts at the root.
3. (Not a code bug, but worth recording) the `/proc` scan for "other Claude
   sessions active" turned up `~/.claude/chrome` — a Claude-in-Chrome bridge
   helper process that also runs the `claude` binary but isn't a coding
   session with a project to name. Excluded anything under `~/.claude`
   itself from the cwd set.

## What's deliberately not done

- **3.7 (multi-session disambiguation) is real but best-effort.** The
  `/proc` scan is a heuristic, not a session registry — it will occasionally
  call something "multiple sessions" that isn't (or miss one that is) if a
  `claude` process's reported cwd doesn't line up cleanly with what a human
  would call "the project." Acceptable because the failure mode is cosmetic
  (a slightly-off or over-eager project name), never silence on the
  highest-value event.
- **`speak.claude_finished.min_turn_secs` is still 0**, i.e. every single
  Stop event speaks — deliberately deferred to Phase 5.1a per docs/04's own
  note ("the right number is found by ear, not by guessing"). No turn-timing
  instrumentation was added in this phase for that reason; there would be
  nothing to tune it against yet.
- **The `Notification` handler doesn't branch on `notification_type`.**
  `idle_prompt` and `permission_prompt` are both spoken as a plain "Claude
  needs you" per docs/01 (`Notification | critical | "Claude is blocked
  waiting for you"` — no sub-case listed). `notification_type` is logged for
  visibility in case that turns out to matter once there's real usage data.

## Acceptance check against docs/04's Phase 3 table

- Walking away from a blocked agent gets you told about it — confirmed live,
  daemon log shows `intent.spoken` for a real critical-priority "Claude
  needs you" style phrase.
- Zero added API tokens — confirmed by design: the short-circuit path never
  touches the LLM, and the long path uses the already-zero-cost local
  `prometheus-llm` (Ollama), never the Claude API.
- Hook failures never block or slow a Claude turn — `async: true` +
  `timeout: 20` in settings.json, every subprocess call inside
  `prometheus-claude` has its own timeout, and the whole dispatch is wrapped
  in a top-level try/except that always returns 0 (the crash-handler bug
  above was caught and fixed specifically because this was tested directly).
- Two concurrent sessions don't produce confusing crosstalk — task 3.7's
  best-effort disambiguation, above.

Task 3.5 (multi-session) is filed under 3.7 in the table above; tasks
3.2-3.6 are otherwise complete as designed.
