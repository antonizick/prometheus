# 2026-09-11 — Kickoff and feasibility

## What happened
Nick proposed a conversational voice layer for Omarchy: a sticky, reboot-surviving
keyboard toggle that makes the OS speak through the existing Piper voice —
commenting on desktop activity and summarizing terminal and Claude Code results.
Constraint: low or no cost, local LLM acceptable. Added mid-session: **toggled-off
must cost effectively nothing**, and the architecture is open to better ideas.

## Verdict
**Feasible. Entirely local. $0 ongoing.** Everything needed is installed or in an
official Arch repo.

## What was actually verified (not assumed)
- **Hyprland event socket works** — connected live, watched this session's own
  window emit events. Immediately exposed the spinner-title spam problem (`◐`/`◑`
  animating in the title several times a second).
- **Piper latency measured** — 0.31 s for a short phrase (including 63 MB model
  load), 0.72 s for a 40-word summary. RTF ~0.07–0.2.
- **Piper supports daemon mode** — `--json-input` (line-delimited stdin) and
  `--output_raw` (streaming) both present on this build. Enables a warm Piper
  with sub-100 ms time-to-first-sound.
- **Speaking rate ≈ 4 words/second** at `length_scale 0.7`. This turned out to be
  the most important number in the project — it's what forces brevity.
- **Voxtype state file** at `$XDG_RUNTIME_DIR/voxtype/state` — solves the audio
  feedback loop.
- **`~/.claude/settings.json` has no `hooks` key** — no conflict; hooks give
  structured access to session results with **zero API token cost**.
- **RTX 2070, 8 GB VRAM**, `extra/ollama-cuda` in the official repo.
- **tmux is not currently running** — so the existing live-terminal-read feature
  does nothing today. Relevant to Q2.

## Where the design departs from the original framing
Flagged because Nick invited better ideas:

1. **Structured data, not screen capture.** Claude Code hooks and shell hooks
   instead of OCR/screenshots. Categorically better input than the current
   approach.
2. **No LLM on the ambient path.** Window/workspace narration is a lookup table.
   An LLM there would add a second of latency and a chance of surprise to
   something that should be instant and perfectly predictable.
3. **The toggle is a power switch, not a mute.** Directly from Nick's mid-session
   constraint. → [ADR-0002](../decisions/ADR-0002-toggle-is-a-power-switch.md)
4. **Pull before push.** Briefing on demand, with only genuinely urgent things
   spoken unprompted. The biggest departure and, I think, the most important.
   → [ADR-0003](../decisions/ADR-0003-pull-before-push.md)
5. **One broker owns the audio device.** Fixes an overlap bug in the *existing*
   TTS scripts too. → [ADR-0001](../decisions/ADR-0001-single-speech-broker.md)

## Deliverables
Full docs in `docs/` (00–07), three ADRs, this note. Nothing installed, nothing
configured, no system changes made — planning only.

## Nick's decisions (end of session)
- **Interrupts:** all four categories on — Claude blocked, command failed, Claude
  finished, *and* desktop activity at ~10–20 % firing, chosen "somewhat
  intelligently" rather than at random.
- **Terminal capture:** exit codes always + opt-in `pr <cmd>` wrapper.
- **Second voice for Claude output:** yes, try it.
- **Non-repetition, across everything.** "This should feel like an artificial
  intelligence, not like I am hearing a script played to me." Overrode my
  template design. → [ADR-0004](../decisions/ADR-0004-generated-variety.md)
- **Config files** to tune options, personality, and to tell it about him. Asked
  explicitly that the answers above be editable settings, not baked-in choices.
  → `config.json` + `persona.md` + `about-me.md`, doc 08.
- *(Register question went unanswered — now a `register` dial in config rather
  than a decision. Default neutral.)*

## The one real design problem, and its fix
Non-repeating phrasing seemed to conflict with both the <300 ms ambient budget
and the zero-VRAM-when-idle guarantee — an LLM call per window focus change would
break both. **Fix: generate variety offline in batches.** A large model writes ~40
phrasings per event type into a bank; runtime is a weighted lookup at <5 ms with
no model loaded. Side benefit: the authoring model can be *bigger* than the
runtime one, since nothing waits on it.

Accepted cost, recorded in ADR-0004: varied phrasing may be harder to tune out
than fixed phrasing. The dial for that is frequency, not repetition.
