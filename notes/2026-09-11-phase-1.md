## The spinner bug turned out to be two bugs

00-feasibility.md's concrete finding was that an animating window title fires
`windowtitle`/`windowtitlev2` several times a second. True, and the fix is in
the one-line rule: those two event types are dropped unconditionally, unread,
at the top of the dispatcher — never parsed, never journaled.

What wasn't documented anywhere, and only showed up from connecting to the
live socket while this very session's title was spinning (mid-turn, the
`◐`/`◑` cursor), is that Hyprland **also re-fires `activewindowv2` on every
title change** for the focused window — not just the title events. A focus
debounce keyed on "did an activewindow event arrive" would never settle while
a title is spinning, because each animation frame would look like a fresh
focus and keep pushing the deadline out. During a long Claude Code turn that
could be minutes.

Fix: the debounce keys off whether the **address** actually changed, not off
event arrival. A repeat announcement of the address that's already pending or
already settled updates a duplicate counter and changes nothing else —
doesn't extend the deadline, doesn't create a new pending state. Verified with
a direct unit test against `Listener._on_activewindow`/`settle_focus`: three
genuine focus changes (a-address b, then c, then back to b) interleaved with
five duplicate re-announcements of the final address produced exactly one
journal entry, `coalesced: 3`, `dupes: 5` internally. Live smoke test over 12s
of this session's own spinning title: `dropped_title=28`ish per run,
`focus_settled=0` (correctly — focus never actually left this window).

## The other real bug, and why the journal was empty at first

`hyprctl clients -j` reports addresses `"0x"`-prefixed (`"0x5622122e3cc0"`);
the raw event socket's addresses are not prefixed (`5622122e3cc0` in
`openwindow`/`activewindowv2`/`closewindow`). `seed_windows()` (which
pre-populates the address→class map from windows already open at startup, so
the very first focus event after a restart can resolve a class) was storing
prefixed keys while lookups used unprefixed ones — silent miss, `cls=None`
every time, empty journal, no error anywhere. Normalized both to the socket's
unprefixed form. Worth writing down because nothing in the Hyprland IPC docs
mentions the inconsistency and it fails quietly rather than loudly.

## Design decisions made while building, and why

**The journal is the *filtered* stream, not raw.** Allowlist (app_names
presence), debounce, and windowtitle-drop all happen before a line is
written — not after. The alternative (journal everything, filter at read
time) would give more data for later tuning, but the Phase 1 acceptance
criteria are explicit about *journal* volume ("zero journal spam", "one event
not six"), and an unbounded raw firehose from every window class on the
system would undermine that. Unknown/unmapped classes are still surfaced —
logged once each at debug level to `prometheus-hypr.log` via `hypr.
unknown_class` — so they can be found and added to `hypr.app_names` without
polluting the journal itself.

**Interest scoring runs offline, in the replay harness — not live in
`prometheus-hypr`.** The build plan gives scoring (1.7) and the replay harness
(1.8) separate tasks specifically so scoring can be validated against real
history before it ever gates a live utterance. `prometheus-hypr` in Phase 1
never calls it and never speaks; a later phase wires the same weights into the
live path once they've been tuned against evidence instead of guesses.

**`prometheus brief` reports everything pulled, not just what scoring would
select.** A deliberate pull (a keypress) is different from ambient chatter —
the point of pulling is "catch me up," not "surprise me with the interesting
bits." So brief and the interest-scored replay are two separate
consumers of the same journal, by design, not one falling out of the other.

**Return-after-absence reuses `novelty_boost` rather than a new config key.**
docs/08's factor table lists it as its own signal, but `config.json`'s
`attention` block (already scaffolded in Phase 0) doesn't have a dedicated
weight for it, and neither does sequence-oddity. Inventing new config keys
that Nick never asked for and hasn't reviewed felt like the wrong call given
"preferences belong in config, not code" — so the replay harness only scores
what's actually configurable today, and says so in its own docstring.

## A third bug: SIGTERM didn't stop the listener

Caught by the overhead re-measurement, not by inspection. `prometheus off`
must reduce Prometheus to zero processes (docs/07's hard contract), but
`prometheus-hypr` stayed in systemd's `deactivating`/`stop-sigterm` state
after the toggle instead of exiting, until systemd's stop timeout elapsed and
SIGKILLed it.

Root cause: the SIGTERM handler only set a Python-level
`shutdown["flag"] = True`. The main loop blocks in
`selectors.select(timeout=None)` — a real blocking syscall — and PEP 475
makes Python transparently *retry* a syscall interrupted by a signal rather
than returning from it, unless the handler itself raises. So the flag was
being set, but nothing ever went back to check it: `select()` just kept
re-blocking forever while idle. `prometheusd` doesn't have this problem
because its shutdown handler calls `broker.shutdown()` directly, which
explicitly notifies the condition variable the speaker thread is blocked on —
an active wakeup, not a flag it hopes gets noticed.

Fixed with the standard self-pipe pattern: `signal.set_wakeup_fd()` writes a
byte to a pipe on every signal, and that pipe's read end is registered with
the same selector as the Hyprland socket and the inotify fd, so `select()`
returns immediately on SIGTERM instead of only on real I/O. Verified directly
(SIGTERM to a bare `python3 bin/prometheus-hypr`, exits within the same
second — previously would have hung until killed) and via the real unit
(`prometheus off` → `systemctl --user list-units 'prometheus*'` now shows
nothing running, where it previously showed `prometheus-hypr.service` stuck
`deactivating`).

Worth remembering for anything built on a bare `selectors`/`select` loop with
`timeout=None`: a Python signal handler that only sets a flag is not enough
to interrupt it. Threading primitives (`Condition.wait`, `Lock.acquire`) don't
have this problem the same way — worth an active notify either way, but the
self-pipe is specifically what a raw selector loop needs.

## Manual dispatch testing was a dead end, not a real gap

Tried to trigger a live focus change from the shell with `hyprctl dispatch
focuswindow ...` to test the debounce end-to-end against real Hyprland
output. This machine's `hyprctl dispatch` goes through an Omarchy Lua command
shim that rejects the dispatcher names/argument syntax tried (`workspace 5`,
`workspace(5)`, `focuswindow class:...`) with Lua parse errors — a config-tool
quirk, unrelated to the code. Real keypresses go through Hyprland's binding
mechanism directly and aren't affected. Validated the debounce logic instead
with a direct unit test driving the listener's internal methods against
synthetic events (see above) rather than rabbit-holing on shell dispatch
syntax.
