## The tag trap docs/03 predicted, hit on the first real run

docs/03 flagged this as a risk before any of this was built: "exact tags to
be confirmed against `ollama list` at install time — the registry moves."
It moved. Plain `qwen3:4b` is no longer the hybrid think/no-think model the
doc was written against — Qwen's 2507 refresh split the 4B size into
separate `-instruct` and `-thinking` releases, and the bare tag now resolves
to thinking-only. It ignores `"think": false` completely, on both
`/api/generate` and `/api/chat`, and spends the entire `num_predict` budget
narrating its own reasoning before ever answering — confirmed by watching a
`"thinking"` field come back full of chain-of-thought for a prompt as simple
as "say OK."

Caught it twice, the second time for real: first in manual testing before
the benchmark existed, then again — despite already knowing better — because
`config.json` still said `"qwen3:4b"` when `bin/prometheus-llm` was run
end-to-end for the first time. It didn't crash. It timed out at the
configured 4s, logged `generate.failed: timed out`, and produced silence —
exactly the fail-silent behavior it was built for, just triggered by the
wrong root cause. `ollama ps` mid-timeout showed the giveaway: `100% GPU`,
model resident, nothing coming back. Fixed by switching to
`qwen3:4b-instruct` in both `config/config.json` and the deployed
`~/.config/prometheus/config.json` (which had drifted from the repo
template — Nick's live system also carries `identity.name: "Lucent"`, not
`"Prometheus"`, from a rename this session didn't touch).

The two candidates that kept their plain hybrid tag — `qwen3:1.7b` and
`qwen3:8b` — do honor `"think": false` correctly on `/api/chat`. So
`prometheus-llm` just sends it unconditionally on every call; it's a
verified no-op on non-hybrid tags like `qwen3:4b-instruct`.

## The other real finding: the prompt's own example gets hallucinated back

docs/03's instruction block includes a negative example: `Say "the auth
middleware", not "src/auth/mw.ts"`. Benchmarking found that weaker models
don't treat it as an example — they report it as the actual outcome,
regardless of what the input said:

- `llama3.2:1b`: 8/20 responses mention "auth middleware" that isn't there.
  One degenerates into a literal repetition loop
  (`"Auth middleware, not src/auth/mw.js. The auth middleware, not..."`),
  and it silently drops a real `FileNotFoundError` traceback as `NOTHING`.
- `llama3.2:3b` — **the documented fallback if 4b feels sluggish** — does
  it 4/20 times, including reporting a real test failure (a missing menu
  item in a desktop-launch test) as *"Authentication middleware returned an
  error message,"* which is exactly the "pass/fail reported backwards"
  failure the acceptance criteria call out by name.
- `qwen3:1.7b` does it 3/20 times, but mildly — tacked-on filler, never a
  wrong outcome.
- `qwen3:4b-instruct` and `qwen3:8b`: zero occurrences.

So `llama3.2:3b` is not currently a safe fallback as prompted, despite
docs/03 listing it as one — full findings and the fix recommendation (stop
using a real-looking file path in the negative example) are in
`experiments/model-bench.md`. Until that's revisited, `qwen3:1.7b` is the
better fallback if `qwen3:4b-instruct` ever needs a lighter alternative:
same family, no hallucinated outcomes observed, 1.7 GB instead of 3.2 GB,
and still comfortably under the latency budget.

A third finding, smaller: every candidate mishandled the one sample that was
a live blocked-agent question rather than a completed outcome — two
hallucinated a result that hadn't happened yet, two silenced it via
`NOTHING`. Not a Phase 2 problem (that content is meant to route through
Phase 3's dedicated `claude_blocked` path, not this general summarizer), but
worth having on record before Phase 3 rediscovers it.

## VRAM release, measured rather than assumed

`experiments/keepalive-results.md`: triggered a real summary through the
real on-demand path (`prometheus-llm` → `systemctl --user start
prometheus-ollama.service` → real GPU load), then polled `nvidia-smi` and
`ollama ps` every 20s. VRAM dropped from 4032 MiB to 895 MiB — back to this
session's idle baseline — 141 seconds after the triggering call, with
`ollama ps` reporting nothing loaded. No manual `ollama stop` involved;
`OLLAMA_KEEP_ALIVE` was left at the configured `5m` throughout, never `-1`.
(Caveat noted in that file: the model was already warm from earlier
benchmarking when the timer started, so 141s is a lower bound on release
time from an in-progress window, not a measurement of the full cold-start-
to-release cycle. The mechanism working automatically is the point, and
that part is solid.)

One open item, not in scope for 2.6 as asked but worth flagging: the
`ollama serve` process itself (as opposed to the model's VRAM) stayed
resident at ~55 MB RSS for as long as `prometheus-ollama.service` was
active, even with no model loaded. `PartOf=prometheus.target` guarantees
it's killed when Prometheus toggles off — the COLD-state contract holds —
but during a long WARM session it's a small, currently-untracked cost
alongside warm Piper's ~100 MB. Stopped manually for now at the end of this
session; a future pass could give the unit its own idle-exit if it turns
out to matter.

## Task 2.4 result

Nick listened to `experiments/listening-preview/`. Piper's output sounded
equally good across every clip — expected, since the voice synthesis is
identical regardless of which LLM wrote the words; that was never the
variable under test. On content: **`qwen3:4b-instruct` sounds better**,
confirmed as the runtime model (matches what was already in config).
`qwen3:1.7b` "could work though if system performance or resource
management forces us to downgrade" — recorded as the resource-pressure
fallback in `config/config.json`'s comments and in
[03-model-selection.md](../docs/03-model-selection.md), replacing
`llama3.2:3b` there (disqualified by the hallucination finding above, not
by the listening test). Phase 2 acceptance table in
[04-build-plan.md](../docs/04-build-plan.md) updated to close out 2.4.
