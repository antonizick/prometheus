# 2026-09-11 — Phase 4 built

Sixth session of the day, after Phases 0-3. Shell integration: `PROMPT_COMMAND`
exit-code narration plus the opt-in `pr` summarizer, per docs/01's
"prometheus-shell" section and Q2 in docs/05.

## What exists now

```
shell/prometheus.bash    Sourced from ~/.bashrc (wired by install.sh). Two
                          pieces:
                          Mode A: a DEBUG trap + PROMPT_COMMAND capture every
                          top-level command's text, exit code, and wall-clock
                          duration (via $EPOCHREALTIME, no forked `date`),
                          then background-dispatch the *decision* to
                          `prometheus-shell exit-code` — this file never
                          decides whether to speak, only whether to ask.
                          Mode B: the `pr` function tees a command's combined
                          stdout+stderr to $XDG_RUNTIME_DIR/prometheus/, keeps
                          the real exit code via PIPESTATUS[0], and
                          background-dispatches to `prometheus-shell pr`.
                          Zero-cost-when-off (ADR-0002): __prometheus_enabled
                          reads the persisted toggle file directly (a bash
                          `read`, no subprocess) before either mode forks
                          anything.
bin/prometheus-shell      The decision backend both modes call into,
                          same shape as bin/prometheus-claude (own Log class,
                          own config load, say()/phrase()/summarize() shelling
                          out to the existing CLIs so dedup/rate-limit/mic-
                          gate/voice-mapping stay owned by prometheusd).
                          exit-code: gated by speak.command_failed /
                          speak.command_succeeded (enabled, min_duration_secs,
                          priority) — already present in config.json,
                          pre-seeded during planning. Below-threshold or
                          disabled -> logged and silent. Otherwise renders
                          command_failed / command_succeeded_long from the
                          phrase bank, with a raw-command-line -> friendly-
                          noun-phrase heuristic (command_phrase(): "the
                          tests"/"the build"/"the install"/"the deploy", or
                          "the command") standing in for the shell text the
                          bank's {command} slot expects — docs/06 forbids
                          speaking a literal command line aloud anyway.
                          pr: reads + deletes the output file, tails it to
                          200 lines / 6000 chars, prepends "Command: ...
                          Exit code: ..." as context, and hands it to
                          `prometheus-llm summarize -c shell`. Always attempts
                          to speak regardless of duration — typing `pr` is
                          itself the opt-in signal, so there's no separate
                          silence threshold on top of it.
install.sh                Adds prometheus-shell to the symlinked binaries and
                          idempotently appends a `source .../shell/
                          prometheus.bash` line to ~/.bashrc (backed up first,
                          same pattern as the Claude settings.json wiring in
                          Phase 3).
```

## Two things found only by testing, before anything was allowed to speak

Consistent with [[prometheus-audible-test-warning]]: everything below was
verified with `say`/`phrase`/`summarize` mocked at the Python level, plus one
real-binary run restricted to inputs guaranteed silent by config (fast
success, and a failure below `min_duration_secs`) — no audio was produced
anywhere in this session.

1. **`bash --noprofile --rcfile <(...) -i` inherited a stray `PROMPT_COMMAND`
   from the *outer* Claude Code bash tool itself** (a terminal-title
   `printf`, apparently part of its own shell-snapshot machinery), which
   showed up as a spurious captured "command" in the first test run. Confirmed
   as a test-harness artifact, not a real bug, by rerunning under `env -i`
   with a fully clean environment — the capture mechanism turned out to
   coexist correctly with a pre-existing `PROMPT_COMMAND` either way (it
   appends via the bash 5.1+ array form, verified separately that this
   preserves an existing string-form `PROMPT_COMMAND` as element 0).
2. **A real bug**: backgrounding the dispatch (`cmd & disown`) still printed
   bash's own job-control `[1] PID` line to the terminal after every
   `pr`-wrapped command — confirmed with a minimal repro that `disown`
   immediately after backgrounding does *not* suppress it, because it's the
   shell's own stderr output for starting the job, not the child's, and
   isn't caught by redirecting the child command's own stdout/stderr.
   Wrapping the whole `cmd & disown` in a group with its own redirect —
   `{ cmd & disown; } 2>/dev/null` — does suppress it (confirmed both ways
   in isolation before changing the real file). Interestingly, the *other*
   dispatch site (inside `__prometheus_shell_precmd`, run via
   `PROMPT_COMMAND`) never showed this in testing — background jobs started
   from a `PROMPT_COMMAND` context don't seem to trigger the immediate
   notice the way one started from a plain top-level or function-body command
   does. Applied the `{ ; } 2>/dev/null` fix to both sites anyway rather than
   rely on that asymmetry, since it costs nothing and removes a
   bash-version/context assumption neither call site actually needs to make.

## What's deliberately not done

- **The captured command *text* is only the first stage of a pipeline or
  the first clause of a compound command** (`sleep 0.3 && false` is logged
  as `sleep 0.3`) — a property of `$BASH_COMMAND` itself, not something this
  file's logic controls. Exit code and duration are still measured correctly
  end-to-end (confirmed in testing: a `&&`-chained failure reported the
  right exit code and the right total wall-clock duration, just under the
  first clause's name). Accepted because `command_phrase()`'s job is a
  substring match, not verbatim transcription, and docs/06 already forbids
  speaking the literal command line regardless.
- **Backgrounded jobs typed directly at the prompt (`sleep 11 && true &`)
  are not reliably narrated.** Traced to the async list forking into a
  subshell that gets its own copy of the bash state variables this file
  uses for capture — mutations inside that child are invisible to the
  interactive parent shell. Not a Phase 4 acceptance criterion, and it's a
  known-hard edge case for this general technique (the same class of issue
  bash-preexec-style tools all have), so left as a documented gap rather
  than chased further.
- **`pr` does not attempt to preserve a TTY for the wrapped command** — its
  stdout is piped through `tee`, so isatty()-sensitive tools (colored output,
  interactive prompts) may behave differently. This is the explicit tradeoff
  docs/05 Q2 already made in choosing options A+B over tmux (C): "sidesteps
  the whole problem of capturing output from an interactive TUI" only holds
  because `pr` isn't trying to be transparent to those tools.
- **No live audible confirmation yet.** The phrase-bank content itself
  (`command_failed`, `command_succeeded_long`) was already reviewed and
  approved by ear in Phase 2 — what's new here is only the trigger mechanism,
  and that's been verified at the logic and CLI-wiring level, not by actually
  hearing a real failed or long-running command through it.

## Acceptance check against docs/04's Phase 4 table

- Fast successful commands produce silence — ✅ true unconditionally right
  now, since `command_succeeded.enabled` defaults to `false`; also verified
  the `min_duration_secs` gate independently for both command_failed and
  command_succeeded so raising `enabled` later doesn't quietly break the
  fast-success case.
- A 40-second failure is announced accurately — logic verified with a mocked
  `say`/`phrase` (a 65s failed `make build` correctly picked the
  `command_failed` bank with `{command: "the build"}`); not yet heard live.
- `pr make test` gives a useful spoken summary — verified end-to-end through
  `handle_pr()` with a mocked summarizer and a real output file (correct
  tailing at 6000 chars, correct cleanup of the temp file in both the
  spoken and the summarizer-returned-nothing cases); not yet heard live.
- Prompt latency increase is unmeasurable — ✅ measured directly: baseline
  ~10 µs/command, hook sourced with Prometheus off ~156 µs/command (the
  `__prometheus_enabled` fast-path file read, no fork), hook sourced with
  Prometheus on ~166 µs/command (adds one backgrounded fork, ~10 µs to
  return). All three are far below human perception; see docs/04.
